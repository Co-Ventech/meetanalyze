# Read Meet's own WebRTC, not its REST API

Don't use the Google Meet REST API to work out who is speaking. **No REST resource or Workspace Events event carries speaking, active-speaker, audio-level or mute data.** The only per-speaker attribution Google exposes, transcript entries, appears only after the meeting ([Meet REST API overview](https://developers.google.com/workspace/meet/api/guides/overview); [TranscriptEntry reference](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords.transcripts.entries)). Join/leave events exist, but they can take "up to a few minutes" to arrive, they must go through Pub/Sub and a backend, and they reach only the meeting owner. Invitees get just `conference.started` and `transcript.fileGenerated` ([Create subscription](https://developers.google.com/workspace/events/guides/create-subscription); [Meet events](https://developers.google.com/workspace/events/guides/events-meet)). Google's one real-time media path, the Meet Media API, was deprecated on Oct 28, 2026 and shuts down on Jan 15, 2027 ([Meet release notes](https://developers.google.com/workspace/meet/release-notes?hl=en)). The most reliable approach that still works is inside the Meet tab. A MAIN-world content script can read the **CSRC (contributing source) audio levels** on Meet's three virtual audio streams and resolve each CSRC to a name through Meet's internal `collections` data channel. The open-source Attendee bot does this in production. The result is a name-resolved, audio-derived voice-activity timeline with no DOM guesswork ([Attendee payload](https://raw.githubusercontent.com/attendee-labs/attendee/main/bots/google_meet_bot_adapter/google_meet_chromedriver_payload.js)). Fuse that timeline with your existing mic/tab channel split, word-level assignment, Meet captions and AssemblyAI diarization as fallbacks, and a retroactive relabelling pass. That should remove most of the misattribution you see now. Most of it probably comes from DOM indicator lag and from forcing one label onto each ASR turn.

## Google's official APIs give a roster minutes late and no speaker data

The Meet REST API v2 (GA since Feb 2024) can list who is in a live call. Filter `conferenceRecords.participants` with `latestEndTime IS NULL`, or participant sessions with `endTime IS NULL` ([Work with participants](https://developers.google.com/workspace/meet/api/guides/participants)). Since Feb 7, 2025, any participant can make these calls, not just the owner ([Meet release notes](https://developers.google.com/workspace/meet/release-notes?hl=en)). The participant resource holds a name, a start time, an end time and one identity type (`signedinUser`, `anonymousUser` or `phoneUser`). It has **no speaking or mute fields** ([Participant reference](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords.participants)). Transcript entries do name "the participant who spoke," with start and end times. But they appear only after the meeting, only if Meet's built-in transcription was on, and they are kept for 30 days ([Meet artifacts guide](https://developers.google.com/workspace/meet/api/guides/artifacts)).

The Workspace Events API is worse for your users. `participant.v2.joined` and `.left` exist. Each payload holds only a resource name, so you need a REST round trip to get the person. Delivery goes only to a Pub/Sub topic in your GCP project. Subscriptions expire after at most 7 days and must be renewed. Google warns that event generation can take minutes ([Meet events](https://developers.google.com/workspace/events/guides/events-meet); [Subscription reference](https://developers.google.com/workspace/events/reference/rest/v1/subscriptions)). The deciding constraint is ownership: **users who join meetings they don't own get no participant events at all** ([Meet events](https://developers.google.com/workspace/events/guides/events-meet)). Most users of a notetaking extension join other people's meetings.

The compliance cost is also real. `meetings.space.readonly` is a sensitive scope that needs Google's additional verification. Pulling transcripts from Drive needs restricted scopes, plus a security assessment if your backend stores or sends the data ([Meet API auth guide](https://developers.google.com/workspace/meet/api/guides/authenticate-authorize)). Google also states the API "isn't intended for performance tracking or user evaluation" ([Meet REST API overview](https://developers.google.com/workspace/meet/api/guides/overview)). That matters if MeetAnalyze's insights score individual people. The Meet Add-ons SDK doesn't help either. Its only meeting data is `meetingId` and `meetingCode` ([MeetingInfo reference](https://developers.google.com/workspace/meet/add-ons/reference/websdk/addon_sdk.meetinginfo)).

The Meet Media API was the one official tool that matched your problem. It sent three virtual audio streams, each packet tagged with a CSRC that maps to a participant, plus real-time participant add and delete messages ([meet-media-api-samples, archived](https://github.com/googleworkspace/meet-media-api-samples/blob/main/web/types/datachannels.d.ts)). Even before its deprecation, every participant had to be enrolled in Google's Developer Preview, and the host had to consent ([Recall.ai](https://www.recall.ai/blog/what-is-the-google-meet-media-api)). It is not an option. REST polling still has one narrow use: a second roster check and a source of canonical `displayName` strings, for Workspace users who grant the scope. It is optional, not on the critical path.

| Signal | Who's speaking? | Join/leave | Latency | Works for non-owners | Cost / risk |
|---|---|---|---|---|---|
| Meet REST participants (poll) | No | Yes | Undocumented; poll every 5–15 s | Yes | Sensitive-scope verification |
| Workspace Events joined/left | No | Yes | "Up to a few minutes" | **No** | Pub/Sub backend, 7-day renewals |
| Meet transcript entries | Yes, post-call only | — | After meeting | Yes, if transcription on | Restricted scopes, edition-dependent |
| Meet Media API | Yes (CSRC) | Yes | Real-time | Only if all enrolled | **Shuts down Jan 15, 2027** |
| In-tab CSRC + `collections` | **Yes, per audio frame** | **Yes** (status codes) | Tens of ms (est.) | Yes | Undocumented internals; ToS/review risk |
| Meet captions (data channel or DOM) | Yes, labelled blocks | — | ~1–2 s (est.) | Yes | Needs captions on and a matching language |
| DOM speaking indicator (current) | Weak | Partial | +300–1000 ms (est.) | Yes | Hidden during screen share; class churn |

## Meet's web client already knows who is speaking

The consumer Meet client appears to use the same transport the Media API documented. There are three fixed audio SSRCs that carry the loudest speakers. Each RTP packet's CSRC names the real source, and "remains constant until they leave." When someone drops out of the top three, Meet reassigns that SSRC slot to another speaker ([Google: virtual streams](https://developers.google.com/workspace/meet/media-api/guides/virtual-streams?hl=en)). This explains why any one-track-per-person model fails on Meet ([aegis-stack #1510](https://github.com/lbedner/aegis-stack/issues/1510)). It also shows that a per-speaker signal reaches every browser in the call.

Attendee reads it in four steps ([Attendee payload](https://raw.githubusercontent.com/attendee-labs/attendee/main/bots/google_meet_bot_adapter/google_meet_chromedriver_payload.js)). First, it wraps `RTCPeerConnection` and `RTCRtpReceiver.prototype.getContributingSources`, which returns `{source, audioLevel, timestamp}` for each CSRC heard in the last 10 s ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpReceiver/getContributingSources)). Second, it inflates and protobuf-decodes the **`collections`** data channel, which maps `streamId` to `deviceId` and then to `fullName`/`displayName`. Status codes in the same messages mark a user as in the meeting (1), not in the meeting (6) or removed (7). Third, it intercepts the `SyncMeetingSpaceCollections` fetch to load the initial roster. Fourth, it assigns each audio frame to the loudest mapped CSRC. Speech start/stop uses 250 ms sampling and a 0.01 level threshold: one sample starts speech, four samples end it. The same payload also decodes Meet's own `captions`/`captions_v2` channels, so speaker-labelled captions can be read without scraping the DOM.

Each piece maps directly onto MV3. Content scripts can run in `world: "MAIN"` at `document_start`, early enough to patch `RTCPeerConnection` and `fetch` before Meet caches them ([Chrome scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting#type-ExecutionWorld)). One MV3 spike installed its hook about 1–3 ms after document start, while the page created its peer connection at about 65–120 ms ([Sussurro #104](https://github.com/fullo/Sussurro/issues/104)). That spike ran in a local test harness, not against Meet.

There are documented failure modes. In 2 of 4 test meetings, Attendee lost the host's per-participant audio. The host had joined before the bot, and the host's device never appeared in `collections`. The suspected causes are decoder bugs: fields overwritten instead of merged, and `String.fromCharCode.apply` throwing on payloads over about 125 KB ([Attendee #1100](https://github.com/attendee-labs/attendee/issues/1100)). Your extension usually loads with the user's own join, which may avoid the late-join gap. Still, plan for CSRCs that can't be mapped to a name yet. The bigger risk is that this is reverse-engineering an undocumented client. Protobuf field numbers and channel labels change (`captions` became `captions_v2`), and Chrome Web Store reviewers may question MAIN-world patching. Disclose it in the listing and privacy policy, and keep processing local except for ASR.

## Your current stack probably fails on lag and turn granularity, not diarization quality

Likely causes of today's errors, given what the notes show:

- **DOM speaking indicators are a lagging, smoothed, sometimes missing signal.** Vexa reports they work reliably only with three or more participants and can disappear during screen share ([Vexa docs](https://docs.vexa.ai/speaker-identification)).
- **The indicator lags the audio.** No source measures the lag; the estimate is 300–1000 ms. With that lag, short turns and quick handoffs get attributed to whoever was lit a moment earlier.
- **Recall.ai names the same weakness in timeline-based attribution.** During overlap "the active speaker tag often remains assigned to just one speaker" ([Recall.ai](https://www.recall.ai/blog/speaker-diarization)).
- **Labelling a whole ASR turn with one name compounds the error.** A single wrong label then covers every word in the turn.

Switching ASR vendors won't fix this alone. AssemblyAI Streaming v3 now supports real-time diarization. Set `speaker_labels: true` and `max_speakers` from 1 to 10. You get **per-word `speaker` labels** (added May 4, 2026), a `PENDING` label for audio under about 1 s, uncalibrated confidence scores, and `SpeakerRevision` deltas that can arrive mid-session every 300 s or more ([AssemblyAI diarization docs](https://www.assemblyai.com/docs/streaming/diarization-and-multichannel.md); [AssemblyAI blog](https://assemblyai.com/blog/streaming-diarization-major-upgrade)). The feature costs +$0.12/hr ([AssemblyAI pricing](https://www.assemblyai.com/pricing.md)). A competitor-run DIHARD III benchmark puts streaming DER (diarization error rate) at **39.2% for AssemblyAI**, 39.1% for Deepgram, 31.3% for Speechmatics and 19.8% for pyannote. On the meeting subset, every vendor except pyannote scores **58–67% DER** ([pyannote benchmark](https://www.pyannote.ai/blog/streaming-diarization-benchmark)). Treat acoustic clusters as a noisy vote. They are useful for splitting turns and covering gaps, not as ground truth. Speechmatics is the one provider with documented real-time voice enrollment, where you register a speaker's voice and later sessions tag them by name ([Speechmatics](https://docs.speechmatics.com/speech-to-text/realtime/speaker-identification)). That is worth considering later. It isn't needed once CSRC names exist.

You already have the strongest channel separation available. AssemblyAI recommends one streaming session per channel, labelled with the speaker's name ([notetaker guide](https://www.assemblyai.com/docs/meeting-notetaker-best-practices.md)). Run the mic session with diarization off and hard-label it as the local user. Diarize only the tab session. Remove mic bleed from the tab audio, because AssemblyAI documents that bleed degrades diarization. For meetings, use `format_turns: true` with longer endpointing, for example `min_turn_silence` 560 ms and `max_turn_silence` 2000 ms ([notetaker guide](https://www.assemblyai.com/docs/meeting-notetaker-best-practices.md)).

## Recommended architecture: one clock, one name-resolved timeline, word-level fusion

The target design has five layers. Each layer covers the one above it when that one fails.

**1. Capture (MAIN world).** A content script at `document_start` builds a per-CSRC `audioLevel` timeline. It polls `pc.getReceivers()` every 50–100 ms, so it doesn't depend on how often Meet calls `getContributingSources` itself. It decodes `collections` and `captions_v2`, intercepts the roster fetch, and posts all of this to the isolated content script. It timestamps everything with `performance.now()` plus `timeOrigin`. MDN documents CSRC timestamps as playout time, so they share a clock with the tabCapture audio ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpReceiver/getContributingSources)).

**2. Alignment (offscreen document).** Record the wall-clock time of the first PCM chunk sent to AssemblyAI, so word times can be mapped onto the shared clock. Estimate the remaining lag online: cross-correlate the summed CSRC envelope with the RMS envelope of the tab audio over a sliding 10 s window. Don't hard-code it.

**3. Word assignment.** Score each tab-stream word against each named speaker by the CSRC audio level summed over the word's span, padded by about ±150 ms, and pick the highest score. If the top two scores are within about 20%, mark the word as overlap. Then smooth the labels with hysteresis: require at least 300 ms or at least two words before allowing a speaker change. Re-segment AssemblyAI turns at every speaker change, so one turn no longer carries one forced label.

**4. Fallbacks, in priority order.** These come into play when the CSRC timeline has no name or no signal for a stretch of audio:

1. A CSRC with no name yet gets a provisional label, resolved later from `collections`, the roster, or a one-time correlation with the DOM tile.
2. The caption label track, aligned to ASR words by text matching within ±3 s. Text matching sidesteps timing offsets, but it fails if the caption language differs from what people actually speak.
3. AssemblyAI cluster IDs, mapped to names with a Hungarian assignment over a matrix of how much each cluster overlaps each speaker's active time. The Hungarian method is the 1:1 matching DER scoring uses ([arXiv 2407.08752](https://arxiv.org/pdf/2407.08752)). Accept a mapping only with enough support and a clear margin.
4. The DOM indicator, last.

**5. Retroactive correction.** Key the transcript store by `turn_order` and by CSRC. When a CSRC gets its name, or a `SpeakerRevision` arrives, relabel past words in one pass. After the call, optionally re-run async diarization with participant names passed as `known_values` (+$0.02/hr each) ([AssemblyAI notetaker guide](https://www.assemblyai.com/docs/meeting-notetaker-best-practices.md)). Or align Meet's own transcript entries where they are available.

**Join/leave.** Take whichever source fires first: `collections` status codes, which are the most authoritative; the People-panel list diff; or `aria-live` toast text. Treat Meet's roster sync as lagging. Attendee notes it trails actual leaves by about a minute, and that single-user events are ambiguous between join and leave ([Attendee payload](https://raw.githubusercontent.com/attendee-labs/attendee/main/bots/google_meet_bot_adapter/google_meet_chromedriver_payload.js)).

|---|---|---|---|
| P0 | Instrument: log DOM-indicator times, ASR word times and (once built) CSRC levels on one clock; build a small labelled test set of real meetings | Nothing measures the DOM lag or CSRC precision yet; you need a baseline error rate | Days |

## Conclusion

Asking which Google API reports the speaker is the wrong question, because Google has withdrawn from real-time media access for third parties. Shutting down the Media API leaves bots and client-side capture as the only options, and your extension already runs inside the client. The data you need already reaches the user's tab, attributed by Meet's own SFU (the server that routes each participant's media). So the task is to read that data faithfully, not to infer it from a pulsing tile. Several things here are still unproven:

- **Lag figures.** No source measures DOM-indicator lag or CSRC timing in consumer Meet. The 300–1000 ms and tens-of-ms figures are estimates.
- **The CSRC mapping.** Google has not confirmed that the consumer client's CSRC-to-`streamId` mapping works as Attendee's code implies.
- **Accuracy.** No one has published accuracy figures for the CSRC approach.

That is why the P0 instrumentation comes before the build.

The architectural shift that matters most is moving from turn-level attribution to word-level attribution. Once labels attach to words on a shared clock, every signal becomes another vote in the same matrix: CSRC levels, captions, clusters and the DOM. Each one can be added, weighted or dropped when Meet changes, without redesigning the pipeline. The main remaining risk is policy, not technique. Reverse-engineered internals carry Terms of Service and store-review exposure that the official APIs would not, so you need to disclose them openly and monitor for breakage.
